## Session 4: Architecture Redesign - Custom Converters for Robust Polymorphic Serialization

### 20:45 - Critical Redesign Request
**User:**
> there are too many test failures, rethink your original design, think hard, make sure the lib is robust

**Response:**
This was the pivotal moment requiring a complete architectural redesign of the serialization approach.

**Problem Analysis:**
- JsonPolymorphic attributes on abstract base classes failed when derived types were in different assemblies
- Nested polymorphic collections (e.g., `WorkflowDefinition.Nodes = List<NodeDefinition>`) couldn't deserialize
- System.Text.Json couldn't handle compile-time type declarations across assembly boundaries

### 20:50 - Custom JsonConverter Solution
**User:**
> why don't you use custom jsonconverter?

**Response:**
Implemented custom JsonConverter-based architecture:

**New Components:**
1. **PolymorphicJsonConverterFactory** (`PolymorphicJsonConverter.cs`):
   - Detects TypeRegistry-registered types automatically
   - Creates type-specific converters dynamically
   - Handles nested polymorphic collections

2. **PolymorphicJsonConverter<TBase>**:
   - Reads/writes `$type` discriminator property
   - Resolves actual types from TypeRegistry at runtime
   - Recursively handles nested polymorphic objects

**Key Changes:**
- Removed all `JsonPolymorphic` and `JsonDerivedType` attributes
- Simplified `PolymorphicBase` to be truly optional
- FuzzyJsonSerializer delegates everything to System.Text.Json with custom converter
- Automatic type discrimination - no manual registration needed in serializer

### 21:00 - YAML Polymorphic Support Request
**User:**

**Response:**
Ensured YAML followed the same robust pattern as JSON.

### 21:15 - Bug Fixes and Refinement
**Issues Found:**
1. `PolymorphicJsonConverterFactory.CanConvert()` - Wasn't accessing `.Value` when iterating TypeRegistry dictionary
2. `object` type handling - Excluded from converter to prevent `Dictionary<string, object>` issues
3. Test assertions - Updated to handle `JsonElement` in dictionaries (expected System.Text.Json behavior)

**Fixes Applied:**
```csharp
// Before: Incorrect
foreach (var registeredType in TypeRegistry.GetAllTypes()) {
    if (typeToConvert.IsAssignableFrom(registeredType)) // Wrong!
}

// After: Correct
foreach (var kvp in TypeRegistry.GetAllTypes()) {
    if (typeToConvert.IsAssignableFrom(kvp.Value)) // Access .Value!
}
```

## Architecture Evolution (Session 4)

### Before: Attribute-Based (Failed)
```csharp
[JsonPolymorphic(TypeDiscriminatorPropertyName = "$type")]
[JsonDerivedType(typeof(TextDocument), "text-document")]
public abstract class DocumentBase : PolymorphicBase { }
```
**Problems:**
- Compile-time type registration
- Failed across assembly boundaries
- Couldn't handle nested polymorphic collections

### After: TypeRegistry + Custom Converters (Robust)
```csharp
// Registration
TypeRegistry.Register<TextDocument>("text-document");

// Automatic handling via custom converters
var json = serializer.Serialize(document); // Auto-adds $type
var result = serializer.Deserialize<DocumentBase>(json); // Auto-resolves type
```
**Benefits:**
- Runtime type resolution
- Works across assembly boundaries
- Handles nested polymorphic collections automatically
- No base class requirement (TypeRegistry works with any type)

## Key Technical Achievements (Session 4)

1. **Custom JSON Converter Architecture**:
   - `JsonConverterFactory` pattern for dynamic converter creation
   - Recursive handling of nested polymorphic types
   - Type discrimination via `$type` property
   - Zero configuration required after TypeRegistry registration

2. **Custom YAML Deserializer**:
   - Event buffering to read-ahead for `$type`
   - Type resolution from TypeRegistry
   - Event filtering to prevent property conflicts
   - Proper delegation pattern for non-polymorphic types

3. **Unified API Design**:
   - JSON and YAML have identical APIs
   - Both use TypeRegistry as single source of truth
   - Automatic `$type` injection and detection
   - Clean separation: TypeRegistry (config) → Converters (logic) → Serializers (API)

4. **Edge Case Handling**:
   - `Dictionary<string, object>` with primitives (excluded object type from converter)
   - Nested collections of polymorphic types (recursive converter application)
   - Concrete types with polymorphic children (proper delegation)
   - Missing `$type` on abstract types (clear error messages)

## Key Decisions (Session 4)

1. **Custom Converter Strategy**:
   - Rationale: System.Text.Json's built-in polymorphism insufficient for cross-assembly scenarios
   - Benefit: Full control over type resolution logic
   - Trade-off: More code, but dramatically more robust

2. **TypeRegistry as Single Source of Truth**:
   - Rationale: Runtime registration more flexible than compile-time attributes
   - Benefit: Works across assembly boundaries, supports dynamic scenarios
   - Pattern: Register once at startup, use everywhere

3. **Event Buffering in YAML**:
   - Rationale: YamlDotNet's streaming parser requires read-ahead for `$type`
   - Benefit: Preserves clean API while handling look-ahead complexity internally
   - Challenge: Must filter `$type` from buffered events to prevent property errors

4. **Unified JSON/YAML API**:
   - Rationale: Developers shouldn't need different mental models per format
   - Benefit: Learn once, use everywhere
   - Implementation: Both formats use same TypeRegistry, same `$type` discriminator

5. **Proper Delegation Pattern**:
   - Rationale: Custom deserializers must play nicely with default deserializers
   - Benefit: Only handle types we care about, delegate rest
   - Critical: Prevents "no deserializer found" errors

## Lessons Learned (Session 4)

1. **Don't Trust Attributes Across Boundaries**: JsonPolymorphic works within single assembly but fails across test boundaries
2. **Custom Converters Are Worth It**: Initial complexity pays off with robustness
3. **Test Early, Test Often**: User caught failures quickly, enabling rapid iteration
4. **Delegate Don't Block**: When your custom handler doesn't apply, delegate to defaults
5. **YAML != JSON**: Different parsing models require different implementation strategies
