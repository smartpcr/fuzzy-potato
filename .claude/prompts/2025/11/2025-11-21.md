### 16:22 - Architecture Change - TypeName Property Introduction
**User:**
> base class should be abstract with abstract prop TypeName, this is used as discriminator, instead of hard coding them

**Response:**
This was a major architectural improvement. Instead of hard-coding discriminators in TypeRegistry.Register() calls, we moved to a property-based approach where each type defines its own discriminator.

**Implementation Steps:**
1. Added abstract `TypeName` property to `PolymorphicBase`
2. Implemented `TypeName` in all concrete types (Document classes and Node classes)
3. Updated serializers to use `TypeName` instead of TypeRegistry lookups
4. Added type caching with assembly scanning to resolve types by TypeName
5. Filtered out `TypeName` property from serialization (both camelCase and PascalCase)

**New Architecture:**
Each polymorphic type now declares its discriminator directly:
```csharp
public class CSharpNode : NodeDefinition
{
    public override string TypeName => "csharp-node";
    // ... properties
}
```

**Type Resolution:**
- Both JSON and YAML serializers now scan loaded assemblies for PolymorphicBase types
- Create instances to get TypeName values and build a cached type map
- No longer require pre-registration in TypeRegistry (though it's still available)

### 16:27 - Simplifying TypeRegistry.Register
**User:**
> do we still need discriminator in this method public static void Register<T>(string discriminator), since it can be retrieved from (Activator.CreateInstance<T>() as PolymorphicBase).TypeName

**Response:**
Excellent observation! Removed the `discriminator` parameter from `TypeRegistry.Register<T>()` method. It now automatically retrieves the discriminator from the instance's TypeName property.

**Before:**
```csharp
public static void Register<T>(string discriminator) where T : PolymorphicBase
{
    var type = typeof(T);
    TypeMap[discriminator] = type;
    ReverseTypeMap[type] = discriminator;
}

// Usage:
TypeRegistry.Register<TextDocument>("text-document");
```

**After:**
```csharp
public static void Register<T>() where T : PolymorphicBase, new()
{
    var instance = Activator.CreateInstance<T>();
    var discriminator = instance.TypeName;
    var type = typeof(T);
    TypeMap[discriminator] = type;
    ReverseTypeMap[type] = discriminator;
}

// Usage:
TypeRegistry.Register<TextDocument>();  // Automatically uses "text-document"
```

## Key Decisions (Session 5)

1. **TypeName as Abstract Property**:
   - Rationale: Forces all derived types to declare their discriminator
   - Benefit: Single source of truth, compile-time enforcement
   - Trade-off: Requires parameterless constructor for type discovery

2. **Assembly Scanning for Type Discovery**:
   - Rationale: Enable automatic type resolution without explicit registration
   - Benefit: More flexible, especially for plugin scenarios
   - Trade-off: Performance cost on first access (mitigated by caching)

3. **Property Filtering in Serializers**:
   - Rationale: TypeName is metadata, not data
   - Benefit: Clean serialized output, $type is the only discriminator
   - Trade-off: Must handle both camelCase and PascalCase naming conventions

## Lessons Learned (Session 5)

1. **Naming Convention Handling**: YAML uses camelCase by default, so property filters must handle both "TypeName" and "typeName"

2. **Type Caching Pattern**: Static dictionary with lock-based initialization provides good performance while supporting dynamic type discovery

3. **Abstract Property for Metadata**: Using abstract properties to provide type-level metadata (like discriminators) is cleaner than external registration

4. **Backward Compatibility**: TypeRegistry.Register() can now be parameterless while maintaining all functionality
